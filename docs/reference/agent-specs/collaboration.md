# 子代理协作的经验

这份是踩出来的，不是设计出来的。每个角色的定义在自己的 `.pi/agents/<角色>.md` 里说**做什么**（`roles.md` 只是索引）；这份说**怎么派、怎么收、什么时候别派**。

写在前面：这些经验里有相当一部分是**主代理**的教训（关于派发方式、节奏、边界），不是子代理的。

## 一、派发之前

### 1. 职责先写文档，用户过目，再真实派出

这是用户的硬规矩：子代理的范围与边界要写到文档里，以后每次工作可以复用；派发要经过用户审核。

理由在实践中反复兑现：职责没写清，子代理就会**自己发明语义**（下面第 5 条）。写文档的成本是一次性的，返工的成本是好几轮。

派发前要落的东西：

| | |
|---|---|
| 角色定义 | `.pi/agents/<角色>.md`（常驻，不随任务改；子代理只读自己那份）|
| 任务上下文 | `docs/tasks/<任务>/context.md`（背景、已定决策、接口与契约、分工、进度表）|
| 契约与生成物 | 契约改动、生成代码、存储列——**主代理做**，子代理等就位 |

### 2. 一波子代理的文件范围必须互斥

这一条是踩出来的：第一波同时派了 be-core（改 `lib/router/**`）和 be-admin（改 `lib/admin/**`、`lib/providers.ts`），结果两个代理都碰了 `lib/router/upstreams.ts`——be-core 甚至因为同时编辑而卡住。

后来那波（core / admin / fe）拆得干净，一波下来没有冲突。**拆的维度是文件，不是功能。**

### 3. 任务要小到「一次能做完」

两个 be-* 代理都撞了 30 分钟超时，留下**半成品**：跨文件的重命名做了一半（`lib/.../deliver.ts` 已经改用新函数名，`upstreams.ts` 还在调用旧名字），于是工作树编译不过。

超时之后：

- **先看工作树**，再决定接手还是重派。不要因为超时就把已写的部分丢掉。
- 半成品跨文件时，主代理要做的第一件事是**把编译修回来**，而不是接着派活。
- 任务描述里写清楚「改哪些文件、每个文件改什么」，别让它自己找。

### 4. 给子代理的任务描述要写死禁令

e2e 代理第一次派出去，它去跑了一个全盘 `find /`，30 分钟耗尽，什么都没交。

重派时加了两条禁令才收敛：

> 不许做全盘扫描（`find /`、扫整个 home）。收敛到最小可跑的场景。`expiry_first` 可以标注为阻塞，不要为了凑一个测试去发真请求。

**凡是会花钱、会改机器状态、会无限扩散的动作，都要写进禁令。**

## 二、子代理交付之后

### 5. 交付要复核，而且要逐条核对

review 代理（fe-review / be-review）的产出里，**有真 bug，也有子代理自己写错的断言**：

- fe-review 找到真问题：前端用 `UpdateProvider` 改策略会抹掉 alias（proto3 普通 string 没有 presence 位）；面板自己数账号数，MiniMax 开放平台一个账号下有多个租户，数错了。
- be-review 找到真问题：注销租户后没删旧凭据 id。
- 也有子代理自己写错的：断言「一个上游失败」，实际是**每个上游各失败一次**。

所以：**review 的结论不能照单全收，要自己看一遍代码再定处置。**

处置的分工按责任边界走：转发侧（`lib/router/**`、`router-proxy.ts`）主代理自己改；admin 侧交回 be-admin。**别让 review 代理改代码**（它是只读的）。

### 6. 契约改动会作废已完成的交付

前端已经按 `UpdateProvider` 写完并通过了测试，契约一改（拆成 `SetProviderPolicy`），那批前端代码要返工。

**教训：契约改动尽早定死，并且立刻广播给所有在飞的子代理。** 如果契约大概率还会动，就先别派前端。

### 7. 子代理返工时，把「已定的决定」连同理由一起给它

返工任务里只写「改成这样」是不够的：子代理会问「为什么不跟原来一样」，或者干脆按自己的理解改回去。

`context.md` 的「已定决策」一节就是干这个的——**写决定和写理由，不只写结论**。

### 8. 主代理自己改代码也要守同一条规矩

这一条是用户明确批评出来的：

> 谁让你动手了，我让你解释清楚。你说了方案我同意了吗？

——在用户只要求「解释清楚」的时候擅自改了代码。**先解释，等同意，再动手。** 主代理没有豁免。

## 三、交付与验收

### 9. 交付用 `context.md` 追加，不另起文件

所有子代理把「改了哪些文件、测试命令与结果、未决问题、给下一个人的交接」追加到同一个 `docs/tasks/<任务>/context.md` 的「交付记录」一节。

好处：主代理读一个文件就知道全局；子代理之间不用互相读文件。

### 10. 验收命令要在任务描述里给全

子代理自己跑一遍本职责的验收命令，不通过不要交。命令要写死（`mise run test:admin`、`cd web && pnpm test`、`mise run web:typecheck`），别让它自己找。

### 11. 离线是硬规矩，但主代理自己也要守

子代理不发真请求（有明文禁令），但主代理在排查时很容易「就发一个试试」。

**真上游额度很小，每次调用都是钱。** 新端点的做法是：录一次响应，转成假上游，之后全用假的。（这条在 `AGENTS.md` 的项目记忆里也有。）

## 四、什么时候不要派子代理

| 情形 | 理由 |
|---|---|
| 改动只有几十行、但需要精确判断 | 派出去的时间比自己做长，而且要复核 |
| 需要跟用户来回确认语义 | 确认在主代理这里做，子代理问不到用户 |
| 排查中途、结论还没成形 | 派出去的是猜测，交付回来也是猜测 |
| 跨层重构（契约 + 存储 + 后端 + 前端） | 契约与存储是主代理的，中间层可以派 |

## 五、几条具体的做法

- **派发用 `subagent` 工具的 workflow 形式**，一次并行多个，互不干扰（文件范围互斥是前提）。
- **交付物要落到文件里**，不要留在对话里。对话会压缩，上下文会丢，文件不会。这份文档就是被压缩逼出来的。
- **子代理的 `output` 绑到文件**（`output` 参数），别让它只在回复里说。
- **主代理读子代理的产出时，只读它写的那个文件**，不要顺着它的思路把自己的上下文也读满——那正是上下文被污染的路径。
