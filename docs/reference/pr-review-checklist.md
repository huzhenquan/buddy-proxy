# PR review 检查清单

`docs/reference/pr-review-process.md` 讲的是**怎么组织**一次 review（双通道、交叉比对、收尾验证）。
这份讲的是**查什么** —— 从这个仓库真实踩过的坑里提炼出来的缺陷模式，每一条都至少让某次
review 误判过一次。

新 session 开场：读 `docs/reference/pr-review-process.md` 拿到流程，读这份拿到判据，然后派单。

写这份的目的只有一个：**同一个缺陷形状不要踩第二次**。所以每条都写清「症状长什么样」，
而不只是「注意 X」。

---

## 0. 三条总则

1. **提交信息不是证据。** 作者说「已修完四条」，那只说明他以为自己修完了。要拿
   `git diff <上次 review 的 head>..HEAD` 去对：改的文件是否真落在那四条上。真实发生过
   一次：提交信息写着 "addresses all of them"，diff 里四条只动了一条。
2. **CI 绿不等于修好了。** CI 只跑测试，测试只覆盖作者想到的路径。真实发生过一次：
   `ClientGoneError` 的翻译在 Qoder 路径写对、在 WorkBuddy 路径漏了，新增测试只测
   Qoder，CI 全绿而缺陷完好。
3. **「测试断言了什么」比「测试是否通过」重要。** 这个仓库的测试曾经把**错误命令**
   固化成预期（`opencode run --prompt`：该 flag 不存在，测试断言的正是那条错命令，
   一路绿灯，真机必然失败）。

---

## 1. 翻译与分类放错层

**症状**：一段「把 A 类错误翻译成 B 类错误」的逻辑写在了外层 `catch`，而需要看到 B 类
错误的判断在内层。

**实例**：客户端断开 → fetch 抛 `AbortError` → 需要被当成 `ClientGoneError`（不冷却、
不换账号）。Qoder 把翻译写在 `run()` 里面（`.catch(e => { throw asClientGone(e, watch) })`），
正确；WorkBuddy 写在外层 `catch`，而 `underPolicy` 的 `onAttempt` 已经先拿到 `AbortError`
并据此写了冷却。

**后果会放大**：一旦把 `signal` 接进 fetch，`fallback` 策略下每个候选都会立即收到同一个
`AbortError`，于是**一次客户端断开把该平台所有账号一起打进冷却**。

**怎么查**：
- `grep -n "instanceof ClientGoneError\|instanceof <YourError>" <文件>` —— 看这个判断所在
  的函数，是否就是抛错那一层的**直接调用方**。
- 把调用链画出来：`run()` → `selectProvider` → `onAttempt(candidate, error)`。任何在
  `onAttempt` 之后才做的翻译都太晚。
- 同一种错误在两条路径上写法不对称时（一条有 `.catch`，另一条没有），优先怀疑没有的那条。

---

## 2. 生命周期窗口：监听器摘得太早

**症状**：`finally { res.off("close", handler) }` 挂在「等响应头」那个 `await` 上，而真正
耗时的操作（读完整个上游流、聚合非流式答复）在它**之后**。

**实例**：`workbuddy.ts` 的 `finally` 在 `underPolicy` 一返回就摘掉监听器，之后的
`aggregateStream` 全程无人监听客户端；客户端的 `'close'` 事件早已发出过，第二次
`once("close")` 永远不会触发。

**判据**：凡是「客户端可能离开」的时间窗，都要有一个活着的监听器覆盖它。窗口包括：
发出请求前、等响应头、读流/聚合、写回客户端。列出这四个阶段，逐一问「这一阶段谁在听」。

**怎么查**：
- 找所有 `off(` / `removeEventListener` / `cleanup()`，问它挂在哪个 `await` 上。
- 找所有 `once("close")`，问它注册的时刻是否晚于 `close` 可能发出的时刻；晚于就要补
  `if (res.destroyed) onGone()`。

---

## 3. 无上限的 `await`

**症状**：等待某个事件（drain、写回调、`close`、上游首帧）的 promise 没有超时，也没有
第二条唤醒路径。

**实例**：`waitForDrain` 无上限 → 客户端连着 socket 却永不读时请求永久挂住，占着上游流与
socket；`destroyed` 检查与 `once("close")` 注册之间存在窗口，`close` 已发过则 promise
永不 settle。

**判据**：这个 `await` 在什么条件下一定会被唤醒？把条件全部列出来（事件、回调、定时器），
少任何一个都可能是永久挂起。

**怎么查**：
- 每个 `new Promise` 里找 `resolve`，问「所有 resolve 路径是否覆盖了『事件早就发生过』
  这一格」。
- 计时口径要看**最早那一帧**而不是「最后一次活动」：按「多久没有新帧」计时会把健康的
  长时间推理误杀。

---

## 4. 假绿：测试参数不构成判据

**症状**：测试写得像那么回事，但它的输入量小到被测行为根本不会发生。

**实例**：背压测试用 800KB（400×2KB）推给一个不读的客户端，注释说「会被 socket 缓冲整个
吸进去」。实测 `res.write` 返回 false 369/400 次 —— 结论对（测试有效），但作者写下的前提
是错的，而按那个前提写的测试换台机器就会变成假绿。改成 256KB×200 ≈ 50MB 才是真判据。

**判据**：把被测实现退回修复前的版本，这个测试会红吗？会红才是判据。

**怎么查**：
- 逐条读断言，问「如果我把它改成恒真，测试还过吗」。
- 对每个「边界条件」测试，问它的输入是否真能触发那个边界（量级、时序、并发度）。
- 反证法：在临时 worktree 里把 `main` 版本的实现换进去，只看测试结果。

---

## 5. 测试把缺陷固化成预期

**症状**：测试断言的正是生产代码里的错误行为。

**实例**：`opencode run -s <id> --prompt "..."` —— `opencode run` 的消息是位置参数，
没有 `--prompt` flag。测试断言了这条错命令，45 项全过，真机一次都发不出去（退出码 1）。

**怎么查**：
- 凡涉及外部 CLI / HTTP API 的调用，拿**对方的**真值校验：`--help` 输出、`--traceResolution`、
  录下来的上游正文。不要只对着自己代码里的常量断言。
- 加一条「对着外部真值校验」的测试，比加十个对着自己常量的断言有用。

---

## 6. 脱敏器两个方向都会错

**症状 A：漏抹。** 按字段名抹 + 按形态抹两层，但某个形态不在任何一层里。

**实例**：UUID 是 36 字符带连字符，既够不到「引号内 40+ 字符」那条规则，也不是 JWT。
字段名叫 `account` / `sub` / `openId` 时就原样进日志。请求 id 恰好叫 `user_id` 才被抹。

**症状 B：过度抹。** 字段名规则用 `tokens?` 这类宽匹配，把 `prompt_tokens` /
`completion_tokens` / `total_tokens` 一起抹了 —— 而这些正是读上游正文时最需要的数字。

**判据**：两个方向都要有断言。「抹掉了应有的」与「留下了不该抹的」是两组测试。

**怎么查**：
- 拿一份真实形状（录下来的上游正文）喂进去，看输出还读不读得懂。
- 列出所有调用点（`grep -rn "scrubForLog" lib/`）—— 挂上去的地方越多，过度抹的代价越大。
- 白名单（`SAFE_FIELDS`）与黑名单（`SENSITIVE_FIELD`）的先后顺序要明确：通常是白名单先判，
  否则 UUID 兜底会把请求 id 也抹掉，排查时对不上上游日志。

---

## 7. 位置参数错位（不报错）

**症状**：两个分支各给同一个函数加了一个位置参数，合并时顺序不同，类型都对，运行时静默
错配。

**实例**：`underPolicy(platform, what, run, settle, <新增参数>)` —— PR 加的是 `life`，
我们分支加的是 `availability`，都合法，都不报错。

**判据**：同一函数有 3 个以上位置参数时，调用点只要有两处以上，就要怀疑。

**怎么查**：
- 合并类 review 必查：`git diff` 里同一函数签名的改动，是否同时在所有调用点改了。
- 建议在 review 意见里要求「新参数并成一个 options 对象」。

---

## 8. 序号与状态没有播种

**症状**：ID 生成靠「现有最大值 + 1」，而计数器行只在「第一次新增」时才存在。

**实例**：`account_seq` 只在该平台第一次新增账号后才创建。升级后「删掉编号最大的旧账号
再加一个」会复用同一个 id —— 而旧 id 的凭据、冷却、快照可能还在。

**怎么查**：
- 找 `max(` / `+ 1` / `nextId` 这类生成逻辑，问「表里没有这一行时怎么办」。
- 删了再加、并发加、跨版本升级，三个场景各推一遍。

---

## 9. 方言与口径的往返不一致

**症状**：A→B 转换再 B→A 回来，数字变了。

**实例**：OpenAI 的 `prompt_tokens` 是全部输入；Anthropic 的 `input_tokens` 只算未命中
部分，命中与写入要另外加。用 `??` 取缓存命中量会拿到 0（上游同时报 `cached_tokens: 0` 与
`prompt_cache_hit_tokens: 88448`），必须取「第一个非零」。

**怎么查**：
- 写一条往返断言：`f(g(x)) === x`，用**真实**的上游数字，不用构造的小整数。
- 看记账层与方言层是否同一口径：两边算出的总数必须相等，否则用量统计会漂。

---

## 10. 「响应头到达就算成功」

**症状**：`fetch` 返回了 200 就当成功，清冷却、记 ok；而正文可能是错误信封、可能读一半
断开、可能客户端早走了。

**实例**：WorkBuddy 用 200 回 `{code:11128,...}`（渠道校验）；Qoder 非流式路同样形状。

**判据**：结算必须发生在**流真正读完且没有错误信封**之后。

**怎么查**：
- 找 `settle.success()` / `clearCooldown()` 的位置，问「正文读完了吗」「读过信封吗」。
- 同一种信封形状在几条路上被识别？真实发生过：流式路认，非流式三条路都不认，同一形状
  三种处理。`grep -rn "isBusinessErrorEnvelope" lib/` 看覆盖是否完整。

---

## 11. 本仓库的七条硬红线

review 的意见里必须逐条给结论（「成立 / 违反 / 未改动」），不能跳过：

1. 响应头到达不算成功；客户端断开不算成功、不写冷却、不换账号。
2. 冷却只在真正失败后写；「等过限流」的标记不得盖住该写的冷却。
3. 402 / 503 / 502 三条语义不许改。
4. thinking 不许拼进 content。
5. 缓存口径：方言层与记账层算出同一个总数。
6. 容器日志不得出现账号标识、令牌、邮箱（脱敏器是最后一道防线）。
7. 不许改上游模型 id、请求头名称与大小写、头的有无。

## 12. 环境与工具注意

这些不是代码问题，但每次都浪费半小时：

- **fork PR 的 CI 卡在 `action_required`**：不是失败，是等维护者批准（`0s`）。用
  `gh api -X POST repos/<owner>/<repo>/actions/runs/<id>/approve` 批准，再看结果。
- **`org/repo` 要显式指定**：本仓库的 `origin` 指向另一个仓库，`gh pr list` 不带 `-R`
  会返回空。
- **临时 worktree 放 `~/projects/worktrees/`**，不要放 `/tmp`：跨文件系统时 pnpm 的硬链接
  退化成复制（247M vs 34M）。
- **worktree 里没有 `web/dist`**：`test/admin-contract-check.ts` 有面板静态托管那一段，
  不先构建面板该段必红。先 `mise run web:build`。
- **不要在 shell 里手敲 `pnpm`**：会继承当前 `NODE_OPTIONS`（Node 26 已删的 flag 会让它直接
  报错）。一律 `mise run <task>` 或 `mise exec -- pnpm ...`。
- **子代理调 `grep`/`find` 不带 `path`**：沙箱把空 path 当仓库根，连续几次就 latch 停机。
  派单时明确要求带 `path`。
- **本地已有 CI 后不必再手动跑 `mise run check`**：看 PR 的 CI 结果即可，`gh pr checks <N> -R <owner>/<repo>`。

## 13. 交付形状

每条意见写清四样，缺一样作者就没法直接动手：

1. **文件:行号**，加上改动后的完整函数（`git show refs/pr/<N>:<路径>`），不能只贴 diff。
2. **判据** —— 违反哪条红线，或什么样的输入会出错。
3. **修法方向**，一两行。有完全正确的对照实现时直接指出来（「照 Qoder 那行抄」）。
4. **不阻塞的观察项单独成段**，不要和阻塞项混在一起 —— 混在一起作者会当成都要改，
   拖慢合并。

结论只用三档：**可合** / **修完再合** / **重做**。

## 14. 不要做的事

- 不要替作者改代码再合：责任混掉，问题面也被掩盖。
- 不要因为测试全绿就跳过读实现。
- 不要在没跑过合并验证的情况下说「可以合」。
- 不要把「提交信息说修了」当成「修了」。
- 不要用「多数表决」解决两位 reviewer 的分歧，用证据。
